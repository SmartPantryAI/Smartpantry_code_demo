# SmartPantry (SMPA)

> AI 기반 식재료 유통기한 관리 & 레시피 추천 서비스
> 융합프로젝트실습 1·2 (2026년) 팀 프로젝트 · 4인 팀

카메라로 영수증이나 식재료를 촬영하면 멀티모달 LLM(Gemma, Ollama)이 자동으로 품목을 인식하고 유통기한을 계산·등록합니다. 유통기한이 임박한 식재료는 매일 웹 푸시로 안내하고, 보유 재료를 기반으로 RAG 기반 레시피 추천까지 제공하는 개인 냉장고 관리 서비스입니다.

## 배경 및 필요성

현대 사회에서 1인 가구 및 맞벌이 가구가 증가하면서 식재료를 대량 구매하기보다 소량 구매하거나 배달 음식을 선호하는 경향이 짙어졌습니다. 하지만 여전히 식재료를 직접 구매해 요리하는 경우, 냉장고 깊숙이 보관된 재료의 존재를 잊거나 유통기한을 놓쳐 버려지는 음식물 쓰레기의 양이 상당합니다.

이렇게 매년 발생하는 음식물 쓰레기는 막대한 처리 비용과 환경 오염을 유발하고, 소비자 입장에서는 구매한 식재료를 활용하지 못하고 폐기하는 경제적 손실로 이어집니다. 이는 체계적인 식재료 관리 시스템의 부재에서 기인한다고 보고, 이를 해결할 서비스를 기획했습니다.

## 목적과 기대효과

본 프로젝트의 목표는 **AI 데이터 기반 유통기한 관리 및 레시피 추천 솔루션**을 구축하는 것입니다.

- AI 기술 도입으로 사용자가 구매한 식재료를 일일이 수기로 입력하는 번거로움을 최소화
- 유통기한 임박 상품을 자동으로 분류해 관리 편의성 극대화
- 분류된 데이터를 토대로 재료에 맞는 레시피를 추천해 식재료의 선순환 구조 형성

기대효과로는 유통기한 경과로 버려지는 식재료의 재구매 지출 감소, 보유 재료 실시간 파악을 통한 중복 구매 방지 및 계획적 소비, 음식물 쓰레기 감소를 통한 환경 오염 방지 및 탄소 배출 저감을 목표로 했습니다.

## 팀 구성 & 담당 역할

4인 팀 프로젝트로 진행했습니다 (조장 김재윤, 조원 전서진·이재용·박성준).

**제 담당은 백엔드 개발**이며, 구체적으로는:

- 프론트엔드 ↔ 백엔드 API 연동 (스캔 이미지 전송, 인식 결과 반환, 레시피 추천 결과 출력, 푸시 알림 발송 등 전체 요청/응답 흐름 설계)
- 소셜 로그인 및 API 키 발급 로직 구현
- 백엔드 ↔ AI 서버(FastAPI) / 외부 LLM 엔진(Ollama) 간 통신 구조 설계 및 연동
- Docker 컨테이너 환경에서 백엔드 서비스 배포 및 운영

## 시스템 아키텍처

```
[웹/앱 (React, PWA)]
   │  스캔 이미지 전송            ▲ 푸시 알림 · 레시피 추천 결과 출력
   ▼                              │
[백엔드 서버 (Node.js / Express)] ──유통기한 확인·데이터 조회/저장──> [DataBase (MySQL)]
   │  스캔 이미지 전달        ▲ 식재료 인식 결과 반환
   ▼                          │
[AI 서버 (FastAPI)] <──이미지 인식 요청/결과──> [외부 LLM 엔진 (Ollama, Gemma)]
   ▲                                                   │
   └──────── 레시피 추천 · 카테고리 분류 요청 (백엔드가 직접 호출) ────┘
```

전체 시스템은 Docker 컨테이너 단위(web, ai, proxy, frontend, db)로 분리 배포했으며, Nginx를 리버스 프록시로 두어 외부 요청을 각 컨테이너로 라우팅했습니다.

## 설계 변경 사항

기획 단계와 실제 구현 사이에 두 가지 중요한 변경이 있었습니다. 두 변경 모두 "정확도"와 "구조 단순화"를 기준으로 판단했습니다.

| 항목 | 기획 | 실제 구현 | 변경 이유 |
|---|---|---|---|
| 이미지 인식 | OCR(PaddleOCR) + YOLO 객체 인식 조합 | 멀티모달 LLM(Gemma-4B, Ollama) 단독 | OCR은 영수증 인쇄 상태·조명에 따라 인식률 편차가 컸고, YOLO는 식재료 클래스별 라벨링 데이터가 추가로 필요했음. 반면 멀티모달 LLM은 별도 학습 없이도 영수증 텍스트와 식재료 이미지를 동시에 처리할 수 있어 정확도와 개발 효율이 모두 더 높았음 |
| 레시피 추천·카테고리 분류 | AI 서버(FastAPI)를 경유해 LLM 호출 | 백엔드가 외부 LLM 엔진을 직접 호출 | 추천/분류 요청까지 AI 서버를 거치면 홉이 하나 늘어 응답 지연이 커짐. 백엔드가 직접 호출하도록 구조를 단순화해 지연을 줄임 |

## 관련 기술 및 채택 이유

**이미지 인식 기술**: 기획 단계에서는 OCR과 YOLO 기반 객체 인식 모델을 결합해 식재료·영수증 이미지를 처리할 계획이었으나, 개발 과정에서 학교/연구실에서 제공하는 Ollama 기반 멀티모달 LLM(Gemma)으로 방식을 변경했습니다.

**추천 시스템**: 사용자가 보유한 식재료 정보를 분석해 만들 수 있는 요리를 추천하는 방식으로 활용했습니다.

**검색 증강 생성(RAG)**: 사용자가 보유한 식재료 목록과 레시피 데이터베이스를 검색 대상으로 삼아, LLM이 실제 보유 재료와 일치하는 레시피 정보를 검색·참조한 뒤 추천 결과를 생성하도록 했습니다. 이를 통해 근거 없는 추천(할루시네이션)을 줄이고 추천의 정확도와 신뢰도를 높였습니다.

## 주요 기능

- **AI 이미지 인식**: 영수증/식재료 사진 촬영 시 Gemma(Ollama, 학교/연구실 제공 공용 서버)가 품목을 인식하고 촬영일 기준 유통기한 자동 계산 및 등록
- **RAG 기반 유통기한 추정**: 식재료별 표준 소비기한 데이터를 검색·참조해 유통기한 추정 정확도 향상
- **가상 냉장고**: 인식된 식재료를 DB에 저장해 실제 물리적 냉장고의 재고를 앱에서도 실시간으로 확인 가능. 보관 유형(냉장/냉동/실온)·카테고리별 필터, D-Day 배지로 임박 상태 시각화
- **유통기한 임박 알림**: 소비기한 3일 이하 남은 식재료를 매일 웹 푸시로 안내 (크론잡 기반 D-1~3 임박 재료 감지)
- **레시피 추천**: 유통기한 임박 재료를 우선순위로 RAG 기반 레시피 매칭 및 추천, 보유/미보유 재료 구분 표시
- **식재료 직접 등록/수정**: AI 인식 외에도 품목명·유통기한·수량·보관 장소를 수동으로 입력/수정 가능
- **관리자 콘솔**: 사용자 관리, 스캔 로그 모니터링, 식품 DB·식재료/낭비 통계, AI 추천 로그, 공지 관리, 감사 로그 등 운영 기능 별도 구현

## 화면 구성 (스토리보드)

일반 사용자 앱과 관리자 콘솔(`/admin`)로 화면을 분리해 설계했습니다.

**일반 사용자 앱**
1. **메인 홈** — 개인화 인사, 식재료 신선 상태 요약 카드, 인식 모드 선택(식재료 촬영/영수증 스캔), AI 레시피 추천 섹션
2. **카메라 스캔** — 식재료/영수증 스캔 모드 구분, Gemma(Ollama) 자동 인식, 촬영 버튼으로 AI 분석 시작
3. **AI 인식 결과** — 인식된 식재료 목록 표시, 품목명·수량·소비기한 탭하여 수정, 보관 장소 선택 후 저장 시 냉장고에 일괄 등록
4. **내 냉장고(저장고)** — 보관 유형 탭(전체/냉장/냉동/실온), 카테고리 필터, D-Day 배지로 임박 시각화
5. **식재료 상세/편집** — 식재료명·보관 장소 표시, 수량 조절, 소비기한 날짜 수정, 폐기 수량 지정 후 삭제
6. **식재료 직접 등록** — 품목명 텍스트 입력, 소비기한 날짜 설정(+1주/+1달/+1년 단축 버튼), 수량·단위 선택
7. **레시피 추천** — 추천/찜한 레시피 탭, AI 추천 배지·난이도·조리 시간, 보유(초록)/미보유(회색) 재료 구분, 찜하기 버튼
8. **마이페이지** — 프로필·사용자 이름, 푸시 알림 받기 토글, 개인정보 설정, 고객센터, 로그아웃

**관리자 콘솔 (`/admin`)**
1. **관리자 로그인** — `/admin` URL로만 접근 가능, `is_admin=1` 계정만 로그인 허용
2. **대시보드** — 전체 사용자/등록 식재료/스캔 수 등 핵심 지표, 소셜 로그인 비율 도넛 차트, 최근 7일 스캔·가입 추이 차트
3. **사용자 관리** — 전체 사용자 목록 조회/검색, 이름·이메일·소셜·식재료 수 표시, 계정 삭제
4. **스캔 로그** — 전체/식재료/영수증/성공/실패 필터, 스캔 썸네일·인식 결과 시각화 (100건 이상 이력 관리, AI 인식 품질 모니터링 목적)
5. **식품 DB** — `ingredients` 마스터 테이블 조회, 보관 유형(냉장/냉동/실온)별 필터
6. **식재료 통계** — 전체 사용자 식재료 등록 횟수 집계, 많이 등록된 식재료 TOP 20 바차트
7. **낭비 통계** — 사용 완료 vs 폐기 수량 집계, 많이 버려진 식재료 TOP 7, 폐기 재료 보관 방법별 분류
8. **AI 추천 로그** — 레시피 추천 이력을 방식(`db_match`/`llm_generated`)별로 필터링해 조회, 추천 품질 모니터링
9. **공지 관리** — 공지 작성/등록, 푸시 알림으로도 발송 옵션, 공지 목록 활성/비활성 관리
10. **감사 로그** — 관리자 활동 이력 전체 조회, 액션 유형별 필터, 시각·액터·액션·IP 기록, 로그인 실패 이력 포함
11. **설정** — 관리자 프로필/역할 표시, 현재 세션 정보(시각/IP/브라우저), 다른 기기 로그인 시 세션 종료 안내

## DB 설계

정규화와 확장성을 고려해 설계했습니다.

**주요 설계 원칙**
- `users` / `social_accounts` 분리 → 소셜 로그인 확장성 확보
- `ingredients` 마스터 테이블 분리 → 식재료명 문자열 중복 제거
- `recommendation_type` 구분 저장 → 추천 방식(레시피 기반/재료 기반 등)별 이력 관리
- `push_subscriptions` 기반 알림 채널 확장 구조
- `scan_logs`에 AI 인식 원본 데이터를 JSON으로 저장 → 인식 결과 추적 및 품질 모니터링

**테이블 목록 (총 16개)**

| 테이블명 | 역할 | 핵심 컬럼 |
|---|---|---|
| users | 사용자 기본 정보 | id, email, name, nickname, is_agreed, is_admin, last_login_at |
| social_accounts | 소셜 로그인 계정 연동 | user_id, provider, provider_user_id |
| ingredients | 식재료 마스터 | id, name, category, emoji, storage_type, default_expiry_days |
| pantry | 사용자 보유 식재료 | user_id, ingredient_id, item_name, expiry_date, category, status, source |
| used_ingredient_logs | 식재료 사용 이력 (낭비 통계용) | id, user_id, item_name, category, quantity, used_at |
| recipes | 레시피 기본 정보 | id, title, description, cooking_time, difficulty, image_url |
| recipe_ingredients | 레시피 구성 재료 | recipe_id, ingredient_id, amount, unit, is_required |
| ingredient_aliases | 상품명→표준 재료명 별칭 매핑 (레시피 매칭용) | alias_name, canonical_ingredient, source |
| recommendation_logs | 추천 이력 | user_id, recipe_id, recommendation_type, match_score, llm_response |
| saved_recipes | 사용자 저장 레시피 | user_id, recipe_name, recipe_json |
| scan_logs | AI 스캔 로그 | user_id, mode, source, image_data, item_count, items_json, status |
| push_subscriptions | 웹 푸시 구독 | user_id, endpoint, p256dh, auth |
| notices | 관리자 공지 | id, message, is_active, push_sent |
| user_consents | 항목별 동의 현황 | user_id, consent_type, agreed, consent_version |
| user_consent_history | 동의 변경/철회 이력 | user_id, consent_type, previous_value, new_value |
| audit_logs | 관리자/시스템 감사 로그 | id, actor, action, target, detail, ip |

**주요 테이블 관계**: `users`는 `social_accounts`/`pantry`/`recommendation_logs`/`saved_recipes`/`scan_logs`/`push_subscriptions`/`used_ingredient_logs`/`user_consents`와 1:N 관계이며, `ingredients`는 `pantry`·`recipe_ingredients`와, `recipes`는 `recipe_ingredients`·`recommendation_logs`와 각각 1:N으로 연결됩니다.

## 핵심 로직

- **유통기한 임박 식재료 조회**: `pantry`와 `ingredients`를 조인해 사용자의 보유 식재료 중 D-3 이내 재료를 조회하고 `days_left` 기준으로 정렬
- **레시피 매칭 점수 계산**: `recipe_ingredients`의 필수 재료를 기준으로 `pantry`와 매칭해 `matched_count`와 `total_required`를 산출하고, `match_score`를 계산해 상위 레시피를 추천

## 배포 환경

```
smartpantry-web       (Node.js)              — 웹 서비스
smartpantry-ai        (FastAPI, uvicorn)     — AI 서버
smartpantry-proxy     (Nginx)                — 리버스 프록시
smartpantry-frontend  (Node 20)              — 프론트엔드
smartpantry-db        (MySQL 8.0)            — 데이터베이스
```

5개 컨테이너로 계층을 분리 배포해 각 서비스를 독립적으로 관리·재시작·확장할 수 있도록 구성했습니다. 개발 환경은 PC/노트북, 서버는 클라우드 서버, 테스트는 실제 스마트폰으로 진행했습니다.

> **운영 중 보안 점검 노트**: MySQL 컨테이너의 3306 포트가 `0.0.0.0`으로 외부에 불필요하게 노출되어 있는 것을 점검 과정에서 발견했습니다. 컨테이너 간 통신은 Docker 내부 네트워크로 충분해 외부 포트 매핑이 원래 필요 없는 구조이며, 이 부분은 후속 조치로 정리가 필요한 상태입니다.

## 개발 프로세스 & 일정

**진행 순서**: 요구사항 분석 → 시스템 설계 → 기능 개발 → 테스트 및 보완

1. **요구사항 분석**: 식재료 등록, 유통기한 관리, 레시피 추천 등 핵심 기능을 정의하고 전체 흐름 설계
2. **시스템 설계**: 시스템 아키텍처와 DB 구조 설계, 사용자 인터페이스 구성
3. **기능 개발**: Ollama로 구동되는 Gemma를 호출해 영수증·식재료 이미지를 인식하고, 추출한 식재료 정보를 DB에 저장하는 기능 구현
4. **추천 시스템 개발**: 보유 식재료 정보를 기반으로 RAG 방식을 적용해 레시피 DB를 검색·참조하고, 이를 근거로 레시피를 추천하는 기능 개발
5. **테스트 및 보완**: 각 기능의 정상 동작 여부 확인, 오류 수정 및 성능 개선

16주 일정 동안 브레인스토밍 → 과제 선정 토론 → 조별/개인별 계획서 작성 → 시스템·DB 설계 → 기능 개발(식재료 인식, 레시피 추천, DB 연동) → 통합 테스트 및 보완 → 최종 보고서 제출 순으로 진행했습니다.

## 트러블슈팅

- **이미지 인식 정확도 문제**: OCR+YOLO 조합은 영수증 인쇄 상태·조명 편차, 식재료 클래스별 라벨링 데이터 부족으로 정확도가 떨어짐 → 멀티모달 LLM(Gemma) 단독 방식으로 전환해 별도 학습 없이 인식률 개선
- **응답 지연 문제**: 레시피 추천·카테고리 분류 요청이 AI 서버를 경유하면서 홉이 늘어 지연 발생 → 백엔드가 외부 LLM 엔진을 직접 호출하도록 구조 단순화
- **DB 포트 노출**: 운영 점검 중 MySQL 3306 포트가 외부에 열려 있는 것을 발견 → 내부 Docker 네트워크만으로 충분해 포트 매핑 제거가 필요하다고 판단, 후속 조치 예정

## 회고

- **잘된 점**: OCR/YOLO 조합 대신 멀티모달 LLM으로 과감히 전환한 결정이 인식 정확도와 개발 속도를 모두 개선함. RAG 도입으로 레시피 추천의 근거 없는 할루시네이션을 줄인 점
- **아쉬운 점**: DB 포트 노출처럼 배포 단계 보안 점검이 개발 초반부터 체계적으로 이루어지지 못한 점
- **다음에 개선하고 싶은 점**: `scan_logs`를 활용한 인식 품질 모니터링 자동화, LLM 응답 지연에 대한 캐싱/비동기 처리 고도화, 낭비 통계 데이터를 활용한 개인화된 절약 리포트 기능
